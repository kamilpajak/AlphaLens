# Saxo WebSocket streaming — design (sub-second fill notification, REST-poll backstop)

**Status:** LOCKED 2026-07-24 (design Workflow + 2 adversarial reviewers; both high-severity findings folded in as hard requirements — absolute-deadline backstop + reconnect circuit-breaker). Protocol CONFIRMED by an exploratory SIM probe (below). Ships DARK, SIM-only (ADR 0014).

> **Guarantee:** streaming is a pure LATENCY win. A total streaming failure degrades to EXACTLY today's poll-only behaviour (never worse). `position_manager.py` is byte-for-byte untouched. The stream thread ONLY calls `wake_event.set()` — the main thread stays the sole executor (no new locks, races impossible).

## ⭐ CONFIRMED PROTOCOL (exploratory SIM probe, 2026-07-24 — build to THIS, not assumptions)
- **Host (resolved):** `wss://sim-streaming.saxobank.com/sim/oapi/streaming/ws/connect?contextId=<ctx>` with header `Authorization: BEARER <token>`. (The other documented convention `streaming.saxobank.com/sim/openapi/streamingws` does NOT resolve on SIM — DNS fail. Keep the empirical two-host fallback but this is the winner.)
- **Subscriptions (REST on the gateway):** POST `/port/v1/positions/subscriptions` + `/port/v1/orders/subscriptions`, body `{ContextId, ReferenceId, Arguments:{ClientKey}}` → HTTP 201, response envelope keys `{ContextId, Format, InactivityTimeout, ReferenceId, RefreshRate, Snapshot, State}` (Snapshot.Data = current rows). **ClientKey scope works** (from `get_client_info()["ClientKey"]`). DELETE `/port/v1/{positions,orders}/subscriptions/{ctx}` → HTTP 202.
- **Binary frame envelope (parser validated on real frames):** `[0:8] msgId u64-LE | [8:10] reserved | [10] refId size (1 byte) | [11:11+n] refId ASCII | [11+n] payload-format byte (0=JSON, confirmed; 1=protobuf, never opted-in→reject) | [next 4] payload size u32-LE | payload`. Multiple messages can be packed in one WS frame — loop.
- **Fill delivery: SUB-SECOND on the `pos` subscription.** A forced market-buy produced an immediate `ref='pos'` frame: msgId=0 = the FULL PositionBase (Amount, PositionId, AssetType…), then PositionView delta frames (price/PnL). Any `pos`/`ord` DATA frame → fire the trigger (never parse deltas — reconcile re-reads full REST state).
- **Heartbeat:** JSON control message `ref='_heartbeat'`, payload `[{"ReferenceId":"_heartbeat","Heartbeats":[{"OriginatingReferenceId":"ord","Reason":…}]}]` (per-subscription); cadence ~20-30s for a quiet subscription → `STREAM_STALE_S=45` is safely conservative.
- **WS lib:** the venv has `websockets` (asyncio) 16.0, NOT `websocket-client`. BUILD DECISION (refines the spec's ws_factory=websocket-client assumption): use `websockets` (asyncio) confined to the dedicated stream thread via `asyncio.run(reader())`; the probe validated connect + recv + parse with it. No new dependency. `websockets>=12` uses `additional_headers=` (older `extra_headers=`) — try/except both.


## Chosen approach
EARLY-WAKE, SINGLE-EXECUTOR streaming (unified Approach A+B) with the two high-severity adversary-2 fixes folded in as hard requirements. The daemon stays single-threaded for everything that decides or mutates protection. A dark, SIM-only Saxo WebSocket reader runs on ONE background daemon thread whose sole cross-thread action is waking the existing loop early via a threading.Event; it never runs reconcile, never places, never touches journals/throttle/oco_lag_counts. `position_manager.reconcile_protection`/`_reconcile_long` are byte-for-byte untouched — streaming changes only WHEN a pass runs. TWO adversary-2 flaws are designed OUT, not merely noted: (1) the blocking `sleep_fn(poll_seconds)` at control_loop.py:410 is replaced by an ABSOLUTE-DEADLINE wait so early wakes give EXTRA passes but never push the guaranteed backstop out; (2) streaming REST (subscription create/delete/reconnect) is HARD-CAPPED by exponential backoff (1s->30s) plus a consecutive-failure circuit breaker that shuts streaming to poll-only, so a reconnect/reset storm can never starve the protective path's per-app-key Saxo rate budget. REJECTED: the naive relative-sleep loop (pushes the backstop past 45s under stale wakes) and unbounded reconnect/resubscribe through the shared client (429-starves protection to ~120s). Neither proposal is BROKEN; the architecture is FIXABLE and every FIXABLE finding is mitigated below.

## Rationale (the never-worse-than-poll guarantee)
The invariant reduces to one question: what bounds the wall-time between consecutive `run_once` calls? `run_once` rebuilds the ProtectionView from live broker state (get_positions + get_long_positions + list_working_sell_orders) and reconciles EVERY call, with no branch that skips/defers reconcile on stream health — so the naked window equals the max gap between passes. Streaming-OFF that gap is `sleep_fn(poll_seconds)` = 45s. Streaming-ON it becomes `wake_event.wait(remaining_to_absolute_deadline)`, whose HARD ceiling is the remaining time to a fixed 45s wall-clock grid; the stream thread can only call `set()`, which makes `wait()` return EARLIER, never later. Absolute-deadline scheduling (advance the backstop deadline ONLY on a timeout-driven pass, never on an early wake) closes adversary-2's timer-reset hole: a stale early wake that sees a not-yet-visible REST position still leaves the next guaranteed pass at the original grid point, so the gap stays <= poll_seconds measured from the last FULL-cadence pass. Bounded streaming REST + circuit breaker closes the 429-starvation hole: streaming's share of the shared coordinated throttle is a hard-capped trickle, so a protective call queues behind at most ~2x _MIN_REQUEST_INTERVAL_S (~1s), never a 120s 429 backoff, and the shared client-side throttle keeps combined traffic under the server limit so self-inflicted 429 is prevented by construction. Every remaining failure collapses to 'Event simply never set -> timeout fires <= poll_seconds', i.e. exactly today's behaviour. This is a pure latency win with a provable never-worse-than-poll floor.

## Trigger wiring (streaming_trigger.py)

CONTROL-LOOP CHANGE (surgical): run_daemon (control_loop.py:393) gains one optional param wake_event: threading.Event | None = None and switches from relative sleep to an ABSOLUTE-DEADLINE interruptible wait (adversary-2 fix #1b). New tail:\n\n    import math\n    if wake_event is not None:\n        assert poll_seconds > 0 and math.isfinite(poll_seconds)  # adversary-1: Event.wait(None/0) must never block forever\n    deadline = monotonic() + poll_seconds\n    while is_running():\n        run_once(deps, sweep_orphans=first); heartbeat_fn(); first = False\n        if once: return\n        now = monotonic()\n        if now >= deadline:            # a TIMEOUT pass just ran -> schedule next backstop grid point\n            deadline = now + poll_seconds\n        if wake_event is None:\n            sleep_fn(poll_seconds)     # legacy/disabled path — byte-identical to today\n        else:\n            wake_event.wait(max(0.0, deadline - now))  # EARLY wakes shrink this; deadline NOT pushed\n            wake_event.clear()\n\nThe backstop deadline advances ONLY when a timeout pass fired (now >= deadline), so any number of stale early wakes cannot push the guaranteed pass past the fixed 45s wall-clock grid. ## Safety net (REST poll backstop)
The ~45s REST poll is preserved verbatim as the stateless backstop and made STRUCTURALLY independent of stream health. wake_event.wait(remaining) has a HARD ceiling of the time to the absolute 45s grid deadline — it returns after at most that whether or not set() is ever called — and the deadline is advanced ONLY by a timeout pass, so run_once (rebuilding the ProtectionView from live positions + live SELL legs and reconciling) runs at least every poll_seconds of WALL CLOCK regardless of stream state: connected, disconnected, silently dead, wrongly-hosted, thread-crashed, circuit-broken, or never started. poll_seconds default STAYS 45.0 and is NEVER lengthened because streaming exists. There is NO branch anywhere that says 'stream healthy -> skip/defer the poll' — run_once is never gated on stream trust/liveness — so the classic broken 'daemon trusts a dead stream' design is absent by construction. Degrade-to-poll needs no fallback code path: if the stream produces nothing the Event is simply never set and the loop times out at the grid deadline. The stream shares NO protection state and holds NO lock the main loop waits on to reconcile (token reads are pushed from main, not pulled by the reader), so a wedged/looping streaming thread cannot stall the protective path. A silent dead subscription therefore costs at most today's <=45s, and the main thread raises a throttled stream-dead alert + a distinct Prometheus gauge so the latency regression from sub-second back to 45s is OBSERVABLE, not silent — but even with zero observability the poll still covers protection.

## Failure handling
DROPPED MESSAGE: reconnect same contextId + &messageid=<_last_message_id> -> server replays buffered messages after that id; usually recovers sub-second, and the poll catches it <=45s regardless. DISCONNECT (_disconnect control msg OR socket EOF/RST): token_provider.invalidate() (a WS auth drop never flows through the HTTP-only 401 seam, so the client invalidates itself), reconnect fresh on the same contextId, recreate subs, snapshot -> on_trigger(); backoff 1s->30s. MISSED HEARTBEAT / SILENT DEAD SUBSCRIPTION / HALF-OPEN TCP (the #1 never-naked hazard): we DO NOT trust silence (heartbeat cadence unpublished). Two layers — (1) stream thread: recv timeout ~30s; if now - last_recv > stale_after_s force reconnect+resubscribe+snapshot+trigger; (2) main thread (authoritative for alerting): each tick reads trigger.seconds_since_last_message(); if > STREAM_STALE_S, deps.alert_throttled('saxo stream silent >Ns — running on poll backstop', 'stream-dead') once per re-alert interval (matching the 2026-07-23 overnight-spam fix) and emits a broker_manager_stream_last_message gauge for an AlphalensBrokerStreamStale rule. STREAM_STALE_S default is <= poll_seconds (default 45s) so the alert does not lag a full poll cycle behind the already-covered protection (adversary-2 fix #5). RECONNECT/RESET STORM: bounded by 1s->30s backoff AND a consecutive-failure circuit breaker (default 6) that shuts streaming to poll-only + alerts, so streaming REST cannot flood the shared throttle and 429-starve the protective place_standalone_stop (adversary-2 fix #2). _resetsubscriptions: DELETE all subs on contextId + recreate with NEW ReferenceIds + fresh snapshot + trigger (a bare socket reconnect is insufficient and is never used for a reset). TOKEN REFRESH MID-STREAM: off-hot-path watchdog compares the main-pushed _current_token to the last-authorized token every ~30s; on change PUT /streamingws/authorize?contextid=<id> BEARER <new> -> 202 (re-auth in place, no reconnect), wired to the same OAuth chain the alphalens-saxo-refresh timer rotates (~20min inside the 40min window); on PUT failure invalidate()+reconnect. The reader NEVER calls get_access_token() inline, so it can never stall on the token flock/network and block the main protective call (adversary-2 fix #4). STATIC TOKEN PROVIDER: cannot re-authorize -> streaming refuses to start, logs once, daemon runs poll-only.

## Thread model
TWO threads, strict single-writer partition, ZERO new locks on the protection path. MAIN daemon thread = the SOLE executor of everything safety-critical: run_once, _run_protection_pass, reconcile_protection, execute_protection closure, every standalone-stop/OCO journal append (_append_standalone_stop_journal open/write/fsync/close), the shared daemon-lifetime _AlertThrottle (_last_sent/_fail_counts/_escalated — verified NOT thread-safe, plain dicts), oco_lag_counts (dict pop/assign in _track_oco_lag), TickReport, AND all stream-dead alerting. Because the streamed trigger runs run_once on THIS thread (the Event only wakes the existing loop; it never spawns a parallel pass), all that state keeps exactly today's single-threaded access pattern — the flagged concurrency races (two protection passes double-committing an OCO before the TTL marker lands; 'dict changed size during iteration' on oco_lag_counts; interleaved journal lines) are IMPOSSIBLE because there is never a second executor. STREAM thread (SaxoStreamingClient reader, daemon=True): connect/recv/parse/reconnect/reauthorize/watchdog. Its ONLY writes visible to main are wake_event.set() (stdlib thread-safe), last_message_epoch (one float, single-writer here), and its own private connection state. It NEVER calls run_once/reconcile, NEVER opens a journal, NEVER touches throttle/executor/oco_lag_counts/TickReport, and NEVER pulls the token (main pushes it via push_token). Shared surfaces are exactly: the threading.Event (thread-safe) and the read-only _current_token holder (atomic str assignment/read). The token FLOCK is touched only by the MAIN thread's existing get_access_token path + the out-of-process saxo-refresh timer — identical to today, no new flock contention. Subscription REST goes through the shared SaxoClient singleton whose _throttle_lock coordinates pacing under the server limit; streaming's throttle share is hard-capped by backoff+circuit-breaker so head-of-line delay to a protective call is bounded to <=2x _MIN_REQUEST_INTERVAL_S (~1s). Startup ordering: _compact_standalone_stop_journal() runs ONCE in build_default_deps BEFORE the stream thread starts, so the compaction rewrite never races the reader. Shutdown: StreamTrigger.stop() sets the stop flag, DELETEs the contextId subs, joins the thread.

## Live SIM probes
- HOST RESOLUTION: `broker stream-probe` on SIM (creds VPS-side) records which of the two documented conventions 101-upgrades; cache the winner
- SUB-SECOND FILL: place a resting order on SIM, force a fill, assert the protection pass (disaster stop / OCO) is placed sub-second via the stream trigger — measure delta vs the ~45s poll baseline
- FORCED DISCONNECT DEGRADES TO POLL: kill the socket / drop the network mid-session, assert the protective stop is still placed within <=45s via the poll backstop (never-naked under stream death)
- TOKEN-REFRESH SURVIVAL: run across a token rotation (force refresh_now or wait the ~20min timer), assert the reader sends PUT /streamingws/authorize -> 202 and the stream survives with NO reconnect and NO delta gap
- RESET-SUBSCRIPTIONS: if observable, provoke or simulate _resetsubscriptions and confirm DELETE+recreate-with-new-ReferenceIds+fresh-snapshot+trigger (not a bare socket reconnect)
- SNAPSHOT SELF-RECONCILE: disconnect, let a fill occur while down, reconnect, assert the connect-snapshot fires one trigger that protects the position

## Bounded windows
- Naked window, streaming ON: hard ceiling <= poll_seconds (45s); typical sub-second on a live fill event
- Backstop cadence: fixed 45s wall-clock grid via absolute deadline; advanced ONLY by a timeout pass, never pushed out by early wakes
- Stream recv timeout: ~30s (force-reconnect trigger inside the reader thread)
- STREAM_STALE_S: default 45s (<= poll_seconds so the alert never lags protection; must be >= the observed ~20-30s heartbeat cadence to avoid false reconnects); configurable
- Reconnect backoff: 1s -> 30s exponential cap
- Circuit breaker: default 6 consecutive reconnect/reset failures within the rolling window -> shut streaming to poll-only + alert once
- Trailing-edge debounce: STREAM_DEBOUNCE_S default 1.0s; last burst member always yields a wake within this window
- Token reauth latency: <= one main tick (~45s) after the out-of-process rotation, comfortably inside the 40min token window
- Head-of-line delay to a protective REST call from streaming subscription traffic: bounded to <= ~2x _MIN_REQUEST_INTERVAL_S (~1s) given the hard-capped streaming cadence — never the 429 [1,120]s backoff

## Open questions (mostly resolved by the probe above)
- SIM streaming host convention: two documented (streaming.saxobank.com/sim/openapi/streamingws vs sim-streaming.saxobank.com/sim/oapi/streaming/ws) — resolve empirically via `broker stream-probe` before coding the constant; picking wrong = stream never opens (fails safe to poll-only)
- Exact heartbeat cadence is unpublished — STREAM_STALE_S is set conservatively (45s) and must be confirmed against the observed SIM cadence in the attended probe
- Positions/orders subscription Arguments scope on SIM: ClientKey vs AccountKey — confirm which returns the intended snapshot for a single-account SIM
- Reconnect buffer window size (how long a drop is replayable via &messageid before the server forces _resetsubscriptions) is not published by Saxo — measure in the probe; the design already assumes no gap-free replay and always ends a reset in a fresh snapshot
- Shared SaxoClient singleton for streaming subscription REST (coordinated throttle prevents self-429) vs a dedicated instance (avoids _throttle_lock head-of-line but risks uncoordinated per-app-key budget): locked to the SHARED singleton + bounded cadence; confirm no head-of-line regression to protective calls under the reconnect-storm probe
- Live-money cutover: live hosts (live-streaming.saxobank.com, gateway/openapi, live.logonvalidation.net), live token scopes, and a fresh never-naked re-validation are OUT OF SCOPE here (ADR 0014 SIM-only) and need their own design pass before trusting streaming with cash
